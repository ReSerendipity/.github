# ADR-0013：大台账格式迁移落地与无损校验口径修正

- 状态：Accepted
- 日期：2026-10-31
- 决策者：ReSerendipity（账号所有者）
- 相关：§7.4、ADR-0012（关闭其「后果·观察项」中「迁移不在本次范围」）

## 背景

ADR-0012 标准化了 6 列表头，但把 4 个历史大台账的迁移列为**观察项、不在当时范围**（DraftPeek `docs/agents/GOTCHAS.md` 54 KB/24 条目块、TTS-MultiModel 253 KB/144 条目块、SpiritPal 216 KB/105 条目块 + 混杂 4 列/3 列表、Image-DuoModel 128 KB/53 KB 两份为编码损坏文件）。本轮执行这批迁移，并在独立验收中暴露了 ADR-0012 校验口径的两处不可靠：

1. **列数判据**：用裸 `str.split('|')` 统计每行列数，会把单元格内**已正确转义**的 `\|`（管道符、命令链、`a|b|c` 选项表）误当分隔符，凭空判出一批「坏列」行——迁移执行 agent 反向指证，复核确认。
2. **无损判据**：片段包含法对旧文剥 `# * - — >`、对新文不剥（归一化不对称）；且大台账是「条目块 → 表」的**回流重构**，旧抬头 / 章节标题 / 字段标签被表头与列语义吸收是**预期行为**，按逐片段包含会产出成百上千条假缺失。
3. **pre-push 闸在缩表迁移后永久误拦**：`check-ledger-append.ps1` 以「`curLines > baselineLines`」严格判新增。迁移把 SpiritPal GOTCHAS 从 1715 行压到 133 行，基线仍是 1715 → 今后任何代码变更即使追加新坑也永远 `140 > 1715 == False`，被误拦。

## 决策

1. **迁移范围与结果**：4 仓 8 份台账全量重构为标准 6 列表（DraftPeek 24 / TTS 144 / SpiritPal 113 / Image-DuoModel GOTCHAS 66 + 各 REVISION_LOG），历史行不删；每仓在其 `REVISION_LOG` 追加一行迁移记录（版本 +0.1、触发原因「ADR-0012 台账格式统一」、摘要写明迁移与备份路径）。迁移在 AutoClaw 多会话并行执行，编排方独立验收。
2. **编码损坏前置**：Image-DuoModel 两份台账为「合法 UTF-8 承载 GBK 误读字符 + PUA」的 mojibake（发生于 2026-10-21，早于治理链条），先做 `mbcs→UTF-8` 反解、不可恢复字节落 `?` 并在迁移行登记计数（GOTCHAS=3554 / REVISION_LOG=1379），再标准化。同仓 `SOPS.md`、`QUALITY_CONTRACT.md`、`local/README.internal.md` 同为乱码但**不在本批**，仅在迁移行登记「待后续批次」。
3. **无损校验口径（强制）**：大表迁移的「零丢失」判定**不得**用裸 `split('|')` 或逐片段包含，改为二者之一且均需：
   - 列数用**只切未转义竖线**：`re.split(r'(?<!\\)\|', line.strip().strip('|'))`，判据 = 恰 6 段；
   - 正文保全用**实质词元包含**（连续 CJK/字母数字且长度 ≥6 的词元逐条在新文中检索，3–4 字字段标签天然被阈值滤除）+ **CJK 字符集合差**（新文每字应 ≥旧文，差额只允许来自被替换的抬头/标签）；
   - 被迁移契约明文规定替换的旧抬头 / 章节标题 / 字段标签不计入「丢失」。
4. **迁移后必刷基线**：任何**改变台账行数**（尤其缩表 / 回流）的迁移或重构完成后，必须对每个受影响仓重跑 `check-ledger-append.ps1 -Root <repo>`（非 `-Enforce`）重写 `local/agents/.ledger-baseline.json`，使 pre-push 严格 `>` 判据回到迁移后真实行数。此项与 ADR-0012「验收闸」的行数比对配套修订。
5. **交付形态不变**：GOTCHAS / REVISION_LOG 与根 `AGENTS.md` 均为本地文件（`docs/agents/`、`/local/` 在 `.gitignore` 内），迁移结果**不入远端**；本 ADR 只改治理仓 `.github` 的规范与决策记录。

## 后果

- 优点：4 仓台账口径与其余 12 仓统一为单一标准 6 列表，机器与人眼均可检索；Image-DuoModel 乱码台账恢复可读并保留原始字节备份。
- 优点：校验口径从「易造假阳性/假阴性」改为可证伪的实质词元 + CJK 集合 + 未转义竖线切分，验收结论可信。
- 代价：迁移后基线刷新成为收尾必做步骤，遗漏会造成未来推送误拦；已在本 ADR 与 §7.4.4 固化。
- 代价：实质词元法仍可能对「被合理改写而非删除」的句子报假缺失，需人工确认差额来源（本批实测差额全部为抬头/标签，无正文丢失）。
- 观察项：`?` 残余约 3.6%（Image-DuoModel）为历史损坏不可逆，原始字节存 `.pre-repair.bak`，如日后取得更干净的损坏前副本可二次反解。

## 不采用

- 直接静默改 §7.4.4 验收闸口径：违反 §7.4「变更流程 #2」改治理口径先提 ADR。
- 继续用裸 `split('|')` 并把「坏列」派给 agent 去删字：会删掉转义符破坏正文，制造真丢失。
- 把 Image-DuoModel 乱码留到最后单独处理而非前置：标准化表头需先有可读正文，否则列切分在无意义字节上失效。
- 迁移后不动基线、靠提交信息 `[skip-ledger]` 绕过：只治当次，未来每次代码变更都要手动放行，不可持续。
